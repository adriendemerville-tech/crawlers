**Adoption : la feature est morte.** 10 analyses au total, dernière le **2026-05-08**, **0 sur les 30 derniers jours**, 4 utilisateurs distincts. Score moyen 74/100.

## 1. Ce qui est bon
- Contexte business très riche et réellement consommé : `tracked_sites` (voice_dna, goals, eeat), `keyword_universe` (top 30 par opportunity_score), `ga4_behavioral_metrics` (page + moyenne site pour comparaison), `content_requirements_matrix` filtré `consumer = 'cro'`, `indexation_checks`.
- Garde-fou d'honnêteté rare : `indexationStatus` avertit explicitement qu'optimiser la conversion d'une page `noindex` / non indexée GSC n'a pas d'impact SEO.
- Enrichissement d'identité en retour (`identity_inference` → `writeIdentity`) quand la carte d'identité est incomplète (< 3/7 champs).
- Analyse d'images (descriptiveness / relevance / persuasiveness) + signaux `chunkability` pour la lisibilité machine.
- 8 `console.log` seulement (hypothèse §H2 du brief invalidée : pas de pollution de logs).
- Index unique `idx_workbench_source_unique` bien en place → l'upsert workbench ne peut plus échouer silencieusement.

## 2. Ce qui est insuffisant (P0)
1. **Aucune sortie workbench en base** : `architect_workbench` compte **0 ligne** avec `source_function = 'analyze-ux-context'`. Le code d'injection existe et est correct, mais il est postérieur aux 10 analyses. Boucle Parménion non prouvée → à valider par un run réel.
2. **Double appel Browserless par analyse** : `captureScreenshotWithAnnotations` puis `findTextPositions` relancent chacun un `page.goto(..., networkidle2, timeout: 45000)`. Coût payant doublé, latence doublée, et risque de désynchronisation screenshot/bounding boxes si la page bouge entre les deux passages.
3. **Timeouts hors norme projet** : 45 000 ms alors que `mem://tech/browserless/timeout-and-semaphore-fix-fr` impose 30 s et un sémaphore 7 slots. Aucun sémaphore ici.
4. **Tracking Browserless dans le vide** : `trackPaidApiCall('analyze-ux-context', 'browserless', ...)` — la table `paid_api_calls` n'existe pas en base. Les appels payants ne sont pas mesurables (le `.catch(() => {})` masque l'échec).

## 3. Ce qui manque (P1)
- **Aucun cache** : réanalyser la même page = repayer LLM + 2 Browserless. Le brief §H5 est confirmé. TTL 7 j invalidé au nouveau crawl serait suffisant.
- **`conversion_visual_captures` : 0 ligne** — l'intégration Pagebolt (capture desktop/mobile) n'a jamais tourné depuis ce module.
- **Monolithe non découpé** : les 3 modes (`default`, `annotations-only`, `manual-suggestions`) cohabitent dans un seul handler de 1 334 lignes.
- **Pas de policy UPDATE** sur `ux_context_analyses` : toute écriture postérieure doit passer par le service client, ce qui bloque une édition côté client.

## 4. Ce qui est trompeur
- Le score global 0-100 est produit par le LLM sans seuil de confiance : une page de 80 mots reçoit un score aussi affirmatif qu'une page de 2 000 mots. Les autres outils (Crawl, Cocoon) ont reçu un garde-fou `inconclusive` (< 30 pages) — pas celui-ci.
- Les bulles ancrées suggèrent une précision pixel qui n'est garantie que si le DOM est identique entre les deux passages Browserless.

## 5. Plan de correction proposé
**P0** — fusionner screenshot + extraction de positions en un seul appel Browserless (une page, un `goto`, screenshot puis mesure des boxes) ; ramener les timeouts à 30 s ; brancher le sémaphore partagé ; supprimer ou recâbler `trackPaidApiCall` vers la table réellement utilisée pour les API payantes.
**P1** — cache `ux_context_analyses` (TTL 7 j, clé `tracked_site_id + page_url`, invalidation au nouveau crawl) ; seuil de confiance (`word_count < 150` → `inconclusive`) ; découpe du handler en 3 modules par mode.
**P2** — relancer la capture Pagebolt, réduire `ConversionOptimizer.tsx` sous 500 lignes.
