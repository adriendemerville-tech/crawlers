# Audit Brief — Infrastructure : architecture DB, server functions, coûts Cloudflare/Supabase, requêtes lentes
Date : 2026-08-20 · Auditeur : Lovable · Baseline : première itération

## 1. Objectif métier
Garantir que la plateforme Crawlers tient la charge et reste rentable : la base de données, les server functions et les edge functions doivent répondre vite, sans requêtes lentes ni dépenses Cloudflare/Supabase/LLM disproportionnées par rapport au chiffre d'affaires par plan.

## 2. Cas d'usage principaux
- Free → lance un audit Marina mono-page → réponse en quelques secondes, coût unitaire quasi nul
- Premium → lance crawl + audit stratégique + cocon → traitement asynchrone en file sans saturer la DB
- Pro Agency → tableaux de bord multi-sites, quotas, équipes → lectures agrégées rapides malgré le volume
- Admin → monitoring live, stats plateforme, coûts LLM → requêtes analytiques sans dégrader la prod

## 3. Logique métier clé
- Périmètre réel constaté : 310 edge functions, 8 modules `*.functions.ts` (server functions TanStack), 2 routes API (`api/public/marina-report`, `api/public/hooks`, `api/external-audit-import`), schéma DB volumineux (types générés ~16k lignes).
- Gating : plans free / registered / agency_pro / agency_premium ; priorités de file 10/20/30/40 ; rôles équipe owner/editor/auditor.
- Dépendances : tables de jobs/queue, `ai_gateway_usage`, `analytics_events`, tables d'audit et de crawl, Lovable AI Gateway (+ override Groq), Browserless, Cloudflare Workers (SSR + server functions).
- Contraintes projet applicables : mem://tech/security/multi-tenant-isolation-fr, mem://tech/queue/batch-processing-system-fr, mem://constraints/agent-spending-limit-fr, mem://tech/browserless/timeout-and-semaphore-fix-fr, mem://constraints/ml-stack-ts-only-fr, mem://tech/performance/track-analytics-non-blocking-fr.

## 4. Critères de qualité attendus
| Axe | Cible | Mesure |
|---|---|---|
| Architecture DB | pas de table orpheline / colonne morte / index manquant sur clés de filtre chaudes ; FK et types cohérents | `supabase--linter`, inspection schéma |
| Requêtes lentes | p95 < 300 ms sur les requêtes applicatives, 0 requête > 2 s en tête de `pg_stat_statements` | `supabase--slow_queries`, `db_health` |
| Server functions | aucune fuite de module serveur vers le client, validation d'entrée systématique, pas de loader protégé sur route publique | revue de code des 8 modules + routes API |
| Coût LLM | < seuil par appel, respect du plafond 1 €/jour agents | `ai_gateway_usage`, `ai_gateway_logs` |
| Coût Cloudflare | pas de fonction déclenchant N+1 requêtes ou du polling agressif ; charge SSR maîtrisée | logs, analytics, revue des crons |
| Sécurité | RLS + GRANT + isolation `auth.uid()` sur toute table exposée | `security--run_security_scan` |
| Volumétrie | tables de logs/analytics avec purge ou rétention définie | requêtes de taille de table |

## 5. Benchmark concurrentiel
- Concurrent 1 : Semrush / Ahrefs — infra de crawl industrielle, files de traitement dédiées, quotas stricts par plan. Force : prévisibilité des coûts. Faiblesse : pas de couche GEO/LLM.
- Concurrent 2 : Screaming Frog (desktop) — coût serveur nul car exécution locale. Force : aucun coût variable. Faiblesse : pas de suivi continu ni de rapports partagés.
- Concurrent 3 : TODO à corriger par l'utilisateur (acteur SEO/GEO français comparable côté architecture SaaS).
- Barre à atteindre / dépasser : coût marginal par audit inférieur au prix du plan le moins cher, avec des temps de réponse perçus comparables à Semrush sur les vues dashboard.

## 6. Périmètre d'audit
### In scope
- Backend : `supabase/functions/**` (focus sur les fonctions chaudes : marina, crawl, autopilot, agents, calculate-*), `supabase/functions/_shared/**`
- Server functions : `src/lib/**/*.functions.ts` (8 modules), `src/routes/api/**`
- DB : schéma public complet (tables, index, RLS, GRANT), `pg_stat_statements`, tailles de tables, crons
- Coûts : `ai_gateway_usage`, logs edge, volumétrie de stockage
### Hors scope
- Design system et UI (audité séparément)
- Contenu SEO / indexation GSC (audits précédents)
- Rapports PDF Marina (déjà traités)

## 7. Signaux à mesurer
- SQL : top requêtes lentes (`supabase--slow_queries`), tailles/lignes par table, index inutilisés, tables sans RLS
- Linter : `supabase--linter` (sécurité + performance)
- Coûts LLM : `select model, count(*), sum(cost) from ai_gateway_usage group by 1 order by 3 desc`
- Logs edge : `supabase--edge_function_logs` sur les 10 fonctions les plus appelées
- Crons : inventaire `cron.job` et fréquences
- Front/Workers : nombre de requêtes réseau par vue clé, polling, taille du bundle
