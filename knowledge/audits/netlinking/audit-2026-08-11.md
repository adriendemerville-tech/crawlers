# Audit — Netlinking
Date : 2026-08-11 · Auditeur : Lovable · Brief : `knowledge/audits/netlinking/brief-2026-08-11.md`

## Verdict global
Module **non opérationnel en production** avant cet audit. Trois défauts bloquants indépendants, chacun suffisant à rendre la feature inutilisable, et une promesse d'interface fausse (3 marketplaces annoncées, aucune réellement joignable). Corrigés en P0 ci-dessous. Le module reste en attente d'au moins une clé API provider pour délivrer de la valeur.

## Défauts P0 (corrigés)
1. **Aucun GRANT sur les 3 tables netlinking.** `netlinking_orders`, `netlinking_providers`, `netlinking_catalog_cache` n'avaient aucun privilège Data API : l'onglet « Mes commandes » et la liste providers échouaient en permission denied côté client. → GRANT ajoutés (SELECT authenticated, ALL service_role, SELECT anon sur providers).
2. **`cron-netlinking-monitor` échouait à chaque exécution** (lundi 07h) : il sélectionnait la colonne `published_url`, inexistante — la table expose `live_url`. Second échec en cascade : l'insert `anomaly_alerts` omettait 5 colonnes NOT NULL (`tracked_site_id`, `z_score`, `current_value`, `baseline_mean`, `baseline_stddev`). → colonne corrigée, alerte complétée avec résolution du `tracked_site_id` par domaine, erreurs remontées dans le résumé.
3. **Webhook provider inatteignable** : `netlinking-webhook` n'était pas déclaré dans `config.toml`, donc `verify_jwt = true` par défaut → tout callback provider recevait 401 avant même la vérification HMAC. Idem pour `cron-netlinking-monitor` appelé par pg_cron sans Authorization. → `verify_jwt = false` déclaré pour les deux (HMAC conservé comme unique garde du webhook).
4. **Providers fantômes** : Rocketlinks et Getfluence étaient `status='active'`, `supports_search/order=true`, sélectionnables dans l'UI, alors que leurs fonctions retournent `[]` (TODO Sprint 2) et que la commande renvoie une erreur *après* débit du wallet. → passés `unavailable`, non sélectionnables dans l'UI, refus serveur en 409 **avant** tout débit.
5. **Aucun gating plan.** N'importe quel compte authentifié pouvait déclencher recherche et commande engageant de l'argent réel. → gating Premium+ (`subscriptions.plan` actif) sur `netlinking-search` et `netlinking-order`, 403 `plan_required`.
6. **Double remboursement possible.** Un replay du webhook `rejected` recréditait le wallet à chaque appel. → refund conditionné à un claim atomique `refunded_at IS NULL`.

## Défauts P1
### Corrigés (2026-08-11, lot P1)
- **Commandes `draft` orphelines** : reaper dans `cron-netlinking-monitor` — après 1 h, la commande passe `cancelled` (claim atomique sur `status='draft'`) et le wallet est recrédité seulement si un débit `netlinking:<id>` existe sans refund correspondant. Compteurs `reaped`/`refunded` dans le résumé.
- **Lien diagnostic → achat** : les findings `low_authority` / `thin_backlinks` / `backlink_target` sont désormais écrits dans `architect_workbench` par `cocoonWorkbench.ts` avec `remediation_channel='netlinking'`, `suggested_anchors` (issues des `anchor_variants`/keywords du maillage interne) et un `deep_link` `/app/console?tab=netlinking&target_url=…&anchor=…`. L'onglet Netlinking affiche un bloc « Opportunités issues du diagnostic » qui pré-remplit la recherche.
- **Réconciliation admin** : fonction `public.netlinking_reconciliation()` (SECURITY DEFINER, gate `has_role(auth.uid(),'admin')`) — débit/refund/net par commande, écart wallet et flag `stale_draft` / `stuck_order` / `missing_refund` / `wallet_mismatch`.

### Restants
- **Aucune clé provider configurée** (`ACCESSLINK_API_KEY`, `ROCKETLINKS_API_KEY`, `GETFLUENCE_API_KEY` absents des secrets). Le module ne peut retourner aucune offre. C'est le seul blocage restant à la valeur métier.
- **Endpoints API Accesslink non validés** (`/v1/marketplace/search`, `/v1/orders`) : écrits à l'aveugle, à confronter à la doc réelle lors du raccordement.


## Défauts P2 (corrigés, lot P2 2026-08-11)
- Couleur violet en dur (`hsl(262,83%,58%)`) sur 5 emplacements → remplacée par les tokens `primary` du design system dans `src/pages/Netlinking.tsx`.
- `netlinking_catalog_cache` : **catalogue volontairement mutualisé** entre comptes. La clé de cache ne contient que des critères de recherche (providers, langue, thème, DR/trafic/budget min) et la payload ne contient que des offres publiques de marketplace — aucune donnée utilisateur, aucune URL cible, aucun `user_id`. Lecture ouverte aux comptes authentifiés par design : elle évite de repayer un appel provider pour une recherche identique. Purge des entrées expirées à chaque appel de `netlinking-search`.
- Quota fair-use sur `netlinking-search` → `check_fair_use_v2` (`netlinking_search`) appliqué **après** le miss de cache seulement, donc un hit de cache ne consomme rien : 20/h et 60/j en Premium, 60/h et 300/j en Agency, 429 `rate_limited` au-delà.


## Signaux mesurés (§7)
- `netlinking_orders` : 0 ligne. `netlinking_catalog_cache` : 0 ligne. `dev_wallet_transactions` avec `source_ref like 'netlinking%'` : 0. Aucune donnée historique → audit qualitatif, pas de baseline de performance.
- `cron.job` : `netlinking-monitor-weekly` bien planifié (`0 7 * * 1`), mais 100 % d'échecs attendus avant correctif.
- Coût LLM : 0 (module déterministe, conforme).

## Prochaine étape recommandée
Fournir une clé Accesslink (ou décider d'un autre provider réellement accessible), puis test de bout en bout : recherche → commande 1 offre à faible montant → vérification débit/refund → exécution manuelle du monitor.
